代理模式

代理模式解决的是“不能或不应该直接访问真实对象”的问题。代理和真实对象通常接口相同，但代理会在访问前后加入控制逻辑。

结构型模式Proxy PatternTypeScript + Python访问控制
🔍 概念速览

代理模式让一个“替身”对象和真实对象实现同一个接口（也就是它们对外提供的一组相同方法），但替身夹在调用方和真实对象之间，在转发请求前后加上控制逻辑（如缓存、权限、延迟加载）。它不改变功能，只控制“能不能访问、怎么访问”。

🤝一句话类比

你想见高管，通常不直接冲进办公室，而是先过助理这关。助理不替高管干活，但会控制见面时机、过滤无效请求。助理和高级别的人对外是“同一套办事方式”，只是助理在中间做了把关。

对照代码：助理 = Proxy，高管 = RealSubject，对外统一的办事方式 = Subject 接口。

虚线框表示接口；Proxy 和 RealSubject 都实现 Subject，Proxy 在构造时接住真实对象并保存，调用时再决定是否转发给它；Client 只认识 Subject。

1. 这个模式解决什么问题

真实对象可能很昂贵、很敏感、在远程，或需要统一控制访问。代理对象站在调用方和真实对象之间，决定是否转发请求、何时创建真实对象、是否直接返回缓存。

为了看清“不用代理”的代价，我们分步来看。

前因：项目里有个远程用户服务，业务一直直接调用它。每次都真打远程，慢而且计费：

class RemoteUserRepository {
  findName(id: string): string {
    console.log("调用远程用户服务"); // 慢、计费
    return id === "u1" ? "Alice" : "Unknown";
  }
}

// 业务直接依赖具体类型，每次都穿透到真实对象
function getName(repo: RemoteUserRepository, id: string): string {
  return repo.findName(id);
}
getName(remote, "u1");
getName(remote, "u1"); // 第二次还是打远程

触发变化：现在产品要求加权限——只有管理员能查用户名，同时要避免重复打远程。于是业务被迫在每个调用点手写判断和缓存：

// 权限 + 缓存被迫写在业务里，且每处查询都要重复这套逻辑
const cache = new Map<string, string>();

function getNameSecure(repo: RemoteUserRepository, id: string, user: { isAdmin: boolean }): string {
  if (!user.isAdmin) throw new Error("无权限");    // 权限逻辑散落
  if (cache.has(id)) return cache.get(id)!;         // 缓存逻辑也散落
  const name = repo.findName(id);
  cache.set(id, name);
  return name;
}

❌ 这就是没有控制点的代价

后果：权限判断、缓存、远程调用全写死在业务调用点里。真实项目里查用户的地方往往不止一处（下单、客服、审计都会查），每加一个地方就要把这套 if + cache 重写一遍；哪天权限规则变了，所有调用点都得翻出来改。更糟的是，远程服务被重复查询直接穿透，没有任何统一拦截。第 6 部分用代理把缓存和权限收口到一个对象里，业务只认 UserRepository 接口。

2. 一个生活类比

你想见一位高管，通常不会直接冲进办公室，而是先通过助理预约。助理不会替高管做所有事情，但会控制访问时机、过滤无效请求、安排日程。助理就是代理。

3. 适用场景

  • 远程服务调用，需要隐藏网络细节。
  • 大对象延迟加载，例如图片、报表、模型文件。
  • 需要权限校验、限流、审计。
  • 同一查询很频繁，可以用缓存代理减少真实调用。

4. 不适用场景

  • 真实对象访问成本低，也没有控制需求。
  • 只是想增加功能组合，更适合装饰器。
  • 代理里塞入大量业务逻辑，导致真实对象职责被掏空。

5. 核心结构

角色职责
Subject真实对象和代理共同遵守的接口。
RealSubject真正完成工作的对象。
Proxy持有或创建真实对象，并控制访问。
Client面向 Subject 编程，不直接依赖 RealSubject。

6. TypeScript 示例

对应第 1 部分的反例，我们写一个代理：它和真实对象实现同一个 UserRepository 接口，把缓存和权限都收口在自己的 findName 里。业务只认接口：

interface UserRepository {
  findName(userId: string): string;
}

class RemoteUserRepository implements UserRepository {
  // 真正访问远程服务的对象
  findName(userId: string): string {
    console.log("调用远程用户服务");
    return userId === "u1" ? "Alice" : "Unknown";
  }
}

// 代理：缓存 + 权限都收口在这里，业务无感
class CachedUserRepositoryProxy implements UserRepository {
  private cache = new Map<string, string>();

  constructor(private real: UserRepository, private canRead: () => boolean) {}

  findName(userId: string): string {
    if (!this.canRead()) throw new Error("无权限查看用户"); // 权限只在一处
    if (!this.cache.has(userId)) {
      this.cache.set(userId, this.real.findName(userId));  // 没命中才打远程
    }
    return this.cache.get(userId)!;
  }
}

// 业务只认 UserRepository，调用方式完全不变
function getName(repo: UserRepository, id: string): string {
  return repo.findName(id);
}

const currentUser = { role: "admin" };
const repo = new CachedUserRepositoryProxy(
  new RemoteUserRepository(),
  () => currentUser.role === "admin"
);
getName(repo, "u1");
getName(repo, "u1"); // 第二次命中缓存，不再打远程；权限仍只判断一次

代理在构造时通过 private real 接住真实对象，findName 时先做权限判断，再查自己的 cache，只有没命中才把请求转发给真实对象。运行会打印：调用远程用户服务 → Alice → Alice（第二次命中缓存，不再访问远程）。反例里散落在各调用点的权限和缓存，现在都收口到代理的这一个方法里。

7. Python 示例

from typing import Protocol


class UserRepository(Protocol):
    def find_name(self, user_id: str) -> str:
        ...

class RemoteUserRepository:
    def find_name(self, user_id: str) -> str:
        # 真正访问远程服务的对象
        print("调用远程用户服务")
        return "Alice" if user_id == "u1" else "Unknown"

class CachedUserRepositoryProxy:
    def __init__(self, real: UserRepository, can_read) -> None:
        self.real = real
        self.can_read = can_read
        self.cache: dict[str, str] = {}

    def find_name(self, user_id: str) -> str:
        if not self.can_read():
            raise PermissionError("无权限查看用户")
        if user_id not in self.cache:
            self.cache[user_id] = self.real.find_name(user_id)
        return self.cache[user_id]

def get_name(repo: UserRepository, user_id: str) -> str:
    return repo.find_name(user_id)

current_user = {"role": "admin"}
repo = CachedUserRepositoryProxy(RemoteUserRepository(), lambda: current_user["role"] == "admin")
get_name(repo, "u1")
get_name(repo, "u1")

Python 同样使用鸭子类型或 Protocol。代理把缓存和权限收口在自己的 find_name 里，业务只认 UserRepository 接口。两次调用中，只有第一次真正访问远程。

8. 优缺点

优点缺点
调用方不需要知道远程、缓存、权限等细节。多一层间接调用，排查链路要看代理逻辑。
可以延迟创建昂贵对象。代理和真实对象接口要保持一致。
集中管理访问控制。如果代理做太多事，会变成隐藏的业务核心。

9. 和相似模式的区别

模式重点区别
代理控制访问决定是否访问真实对象，常见于权限、缓存、懒加载。
装饰器增强能力重点是叠加行为，通常可多层自由组合。
适配器接口转换改变接口形状，让不兼容对象可用。

一句话区分：简单包装不改方法、只是套壳；装饰器不改签名，给对象“加料”增强功能；代理同样保持相同接口，但它不增强功能，而是控制“是否/何时访问真实对象”（缓存、权限、懒加载）——这才是它和“简单封装”的本质不同。

今日总结

代理模式的核心是“接口相同，访问受控”。当你需要缓存、权限、懒加载或远程调用隔离时，可以考虑代理。
