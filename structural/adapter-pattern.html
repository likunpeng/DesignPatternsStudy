适配器模式

适配器模式解决的是“已有对象能用，但接口不符合当前系统要求”的问题。它让新旧接口可以协作，而不是强行改动稳定代码。

结构型模式Adapter PatternTypeScript + Python接口转换
🔍 概念速览

适配器模式把一个类的接口（也就是它对外提供的一组方法），转换成调用方期望的另一个接口，让原本因接口不兼容而不能一起工作的类可以协同工作。它只做“接口翻译”，不改变原有功能。

🔌一句话类比

笔记本只有 USB-C 口，投影仪只有 HDMI 口；两边都能用，只是口对不上。转接头不做任何“新功能”，只把 USB-C 信号转成 HDMI——它就是适配器。

对照代码：转接头 = Adapter，笔记本 = Client，投影仪 = Adaptee，笔记本期望的接口（USB-C）= Target。

角色关系
Client业务代码
依赖 ▸
Target期望接口
◂ 实现
Adapter转换层
调用 ▸
Adaptee已有对象

虚线框表示接口；Adapter 实现 Target 接口，内部调用 Adaptee；Client 只认识 Target，完全不感知 Adaptee 的存在。

今日目标

  • 理解适配器模式为什么不是简单封装。
  • 能识别接口不兼容导致的耦合问题。
  • 能用 TypeScript 和 Python 实现一个最小适配器。
  • 知道适配器和外观、代理的区别。

1. 这个模式解决什么问题

把视角切回真实场景：你的笔记本只有 USB-C 口，会议室的投影仪只有 HDMI 口。两边都能用，只是口对不上，直接插不进去。

// 没有适配器：笔记本被迫直接认投影仪的 HDMI 口
projector.receiveHdmi(signal);   // 笔记本亲自懂 HDMI，换 VGA 显示器就全要改

问题在这里：笔记本为了用上投影仪，直接去调它的 HDMI 口——等于笔记本被迫"懂 HDMI"。换一台 VGA 老显示器，每个调用点都要改成认 VGA；哪天投影仪换了个口，散在各处的转换代码都得翻出来改。笔记本其实只想做一件事——把画面送出去——根本不想管对面是什么口。

适配器要做的，就是在笔记本和投影仪之间塞一个"转接头"：笔记本只发一句统一的"USB-C 信号"，转接头负责把它变成投影仪能收的 HDMI。换设备时，笔记本一行不用动，只换（或加）一个转接头即可。第 6 部分会用代码把这个转接头落地。

2. 一个生活类比

笔记本只有 USB-C 口，投影仪只有 HDMI 口；电脑能出画面，投影仪能放画面，只是接口对不上。转接头就是适配器：它不动电脑也不动投影仪，只把 USB-C 信号转成 HDMI。

3. 适用场景

  • 接入第三方 SDK，但它的方法名、参数单位或返回结构和系统约定不同。
  • 改造遗留系统，希望新代码使用统一接口。
  • 多个供应商能力类似，但接口细节不同。
  • 测试时需要把复杂外部服务适配成简单接口。

4. 不适用场景

  • 接口可以直接修改，而且没有外部依赖或历史包袱。
  • 只是想给方法改个名字，增加适配器反而让代码绕。
  • 业务规则本身不同，不只是接口形状不同。

5. 核心结构

角色职责
Target当前系统希望使用的目标接口。
Adaptee已有对象或第三方对象，功能可用但接口不匹配。
Adapter实现目标接口，并在内部调用 Adaptee 完成转换。
Client只依赖 Target，不关心背后接的是谁。

6. TypeScript 示例

对应第 1 部分，我们写一个 USB-C 转 HDMI 的转接头，让投影仪能用上笔记本期望的接口。笔记本从此只认一个接口：

interface ExternalDisplay {   // Target：笔记本期望的接口（插上 USB-C 就能投屏）
  receiveUsbC(signal: string): void;
}

class HdmiProjector {         // Adaptee：投影仪，只有 HDMI 口
  receiveHdmi(signal: string): void {
    console.log(`HDMI 投影仪投放：${signal}`);
  }
}

// 转接头：实现笔记本期望的 USB-C 接口，内部把信号转成 HDMI
class UsbCToHdmiAdapter implements ExternalDisplay {
  constructor(private device: HdmiProjector) {}
  receiveUsbC(signal: string): void {
    this.device.receiveHdmi(signal); // 适配发生在“口”上，不关心内容
  }
}

// 笔记本只认 ExternalDisplay，不关心对面是 HDMI 还是别的口
function present(display: ExternalDisplay) {
  display.receiveUsbC("季度复盘幻灯片");
}

present(new UsbCToHdmiAdapter(new HdmiProjector()));

present（代表笔记本）只认识 ExternalDisplay，完全不感知背后是 HDMI 投影仪还是别的设备。笔记本发的是 USB-C 信号，真正的 HDMI 调用被关在转接头里。如果会议室还有一台 VGA 老显示器，只需再写一个 UsbCToVgaAdapter，笔记本代码一行都不用改。运行会打印 HDMI 投影仪投放：季度复盘幻灯片。

真实项目里这种“口不匹配”最常出现在接入第三方 SDK——比如支付网关：有的叫 charge(分)，有的叫 processPayment(元)。结构完全一样，只是转换内容从“信号格式”变成“金额单位”。本文用笔记本 + 投影仪，是为了和开头类比保持一致，让你只建立一幅心智模型。

7. Python 示例

from typing import Protocol



class ExternalDisplay(Protocol):     # Target：笔记本期望的接口（插上 USB-C 就能投屏）
    def receiveUsbC(self, signal: str) -> None:
        ...

class HdmiProjector:                # Adaptee：投影仪，只有 HDMI 口
    def receiveHdmi(self, signal: str) -> None:
        print(f"HDMI 投影仪投放：{signal}")

class UsbCToHdmiAdapter:            # 转接头：实现 USB-C 接口，内部转成 HDMI
    def __init__(self, device: HdmiProjector) -> None:
        self.device = device

    def receiveUsbC(self, signal: str) -> None:
        self.device.receiveHdmi(signal)

def present(display: ExternalDisplay) -> None:
    display.receiveUsbC("季度复盘幻灯片")

present(UsbCToHdmiAdapter(HdmiProjector()))

Python 更自然地使用鸭子类型或 Protocol。只要对象有 receiveUsbC 方法，就能被 present 使用。这个适配器和 TypeScript 版本承担完全相同的职责：把投影仪的 HDMI 口收口到笔记本期望的 USB-C 接口后面。

8. 优缺点

优点缺点
隔离第三方或遗留接口，调用方更稳定。类数量增加，简单场景可能显得多余。
转换逻辑集中，便于替换外部实现。适配器过多时，需要统一命名和组织。
符合开闭原则，新增供应商通常只加新适配器。只能解决接口不兼容，不能解决语义不一致。

9. 和相似模式的区别

模式重点区别
适配器接口转换已有对象接口不符合当前系统。
外观简化复杂子系统不是为了兼容接口，而是为了降低使用复杂度。
代理控制访问代理通常保持相同接口，增加权限、缓存、延迟加载等控制。
装饰器增强功能装饰器保持相同接口，给原对象“加料”（日志、缓存等）；适配器则是转换接口、不改功能。

一句话区分：简单包装不改方法签名，只是套个壳；装饰器不改签名，但给对象“加料”（增强功能）；适配器恰恰要改写方法签名，把 Adaptee 的接口对齐到 Target —— 这才是它和“简单封装”的本质不同。

10. 练习题

你的系统统一使用 send(to, content) 发送短信，但某短信平台 SDK 只有 pushSms(phone, text, sign)。请设计一个适配器，让业务代码不依赖该 SDK。

参考思路：定义 SmsSender 接口，再实现 VendorSmsAdapter，把 send 的参数转换成平台需要的参数，并在适配器中补充签名。

今日总结

适配器模式的核心是：不要让调用方到处理解外部接口差异。把差异封装在适配器里，让业务代码依赖自己的稳定接口。
