桥接模式

桥接模式解决的是“两个变化维度互相绑死，导致类数量爆炸”的问题。它把抽象和实现拆开，让它们可以独立变化。

结构型模式Bridge PatternTypeScript + Python组合优于继承
🔍 概念速览

桥接模式把抽象（也就是它对外提供的一组方法）和具体实现拆成两层，用“组合”连接，让两个变化维度可以各自独立扩展，而不必为每种组合都写一个子类。它只做“解耦维度”，不改单个功能。

📺一句话类比

遥控器和电视品牌是两个变化维度。遥控器有基础版、高级版（抽象维度），电视有各品牌（实现维度）。如果每个遥控器都绑定一个品牌，类会越来越多。桥接的做法是遥控器持有一个“电视接口”，不绑定具体品牌——换电视只换实现，遥控器照用。

对照代码：遥控器 = Abstraction，高级遥控器 = RefinedAbstraction，电视接口 = Implementor，具体电视 = ConcreteImplementor。

角色关系
Abstraction抽象层
持有 ▸
Implementor实现接口
◂ 实现
ConcreteImplementor具体实现

虚线框表示接口；Abstraction 持有 Implementor 接口（不绑定具体实现），调用时转发到 ConcreteImplementor。RefinedAbstraction 是 Abstraction 的变体，两个维度各自扩展、互不影响。

今日目标

  • 理解桥接模式为什么能减少继承层级。
  • 识别两个独立变化维度。
  • 能用组合把抽象层和实现层连接起来。
  • 能区分桥接和适配器。

1. 这个模式解决什么问题

如果一个系统有两个独立变化维度，直接用继承会产生组合爆炸。

通知类型：普通通知、紧急通知
发送渠道：邮件、短信、微信

继承方案需要：
  NormalEmailNotification
  NormalSmsNotification
  NormalWechatNotification
  UrgentEmailNotification
  UrgentSmsNotification
  UrgentWechatNotification
每增加一种类型或渠道，都要翻倍。

把上面的组合直接写成代码，紧耦合和重复就暴露出来了：每加一个渠道，普通 / 紧急两种类型又各要补一个类。

❌ 反例（不要这样写）

// 两个维度用继承绑死，类数量 = 类型 × 渠道，呈组合爆炸
class NormalEmailNotification { /* 发邮件 */ }
class NormalSmsNotification { /* 发短信 */ }
class NormalWechatNotification { /* 发微信 */ }
class UrgentEmailNotification { /* 发邮件 + 紧急 */ }
class UrgentSmsNotification { /* 发短信 + 紧急 */ }
class UrgentWechatNotification { /* 发微信 + 紧急 */ }
// 再新增一个渠道，必须再写 NormalXxx + UrgentXxx 两个类

这样“通知类型”和“发送渠道”被绑死在继承里，新增任一维度都要翻倍数，逻辑也大量重复。第 6 部分用桥接把两层拆开，类数量从 M×N 降到 M+N。

2. 一个生活类比

遥控器和电视品牌是两个变化维度。遥控器可以有基础版、高级版；电视可以是不同品牌。如果每个遥控器都绑定一个电视品牌，类会越来越多。更好的做法是遥控器持有一个电视接口。

3. 适用场景

  • 两个维度都可能扩展，并且可以独立变化。
  • 继承层级已经因为组合关系变得臃肿。
  • 希望运行时切换实现。
  • 抽象逻辑和底层实现需要分开演进。

4. 不适用场景

  • 只有一个变化维度。
  • 组合关系并不稳定，强行抽象会增加理解成本。
  • 简单业务中几个类就能解决问题。

5. 核心结构

角色职责
Abstraction抽象层，面向业务提供高层能力。
RefinedAbstraction抽象层的具体变体。
Implementor实现层接口。
ConcreteImplementor实现层的具体实现。

6. TypeScript 示例

// 实现层接口：定义“发送消息”这个能力，不关心具体是哪种渠道
interface MessageSender {
  send(content: string): void;
}

// 具体实现 A：邮件渠道（实现维度）
class EmailSender implements MessageSender {
  send(content: string): void { console.log(`邮件：${content}`); }
}

// 具体实现 B：短信渠道（实现维度）
class SmsSender implements MessageSender {
  send(content: string): void { console.log(`短信：${content}`); }
}

// 抽象层：构造时通过组合接住一个 MessageSender 实现对象，不绑定具体渠道
class Notification {
  constructor(protected sender: MessageSender) {}
  // 通知时把请求转发给实现层，自身只负责“通知”这件事
  notify(content: string): void { this.sender.send(content); }
}

// 抽象层变体：紧急通知，属于“通知类型”维度，与渠道维度互不干扰
class UrgentNotification extends Notification {
  notify(content: string): void { this.sender.send(`[紧急] ${content}`); }
}

// 运行时自由组合两个维度：紧急+短信、普通+邮件，类数量从 M×N 降到 M+N
new UrgentNotification(new SmsSender()).notify("服务器 CPU 过高");
new Notification(new EmailSender()).notify("日报已生成");

Notification 在构造时通过 protected sender 接住一个 MessageSender 实现对象并保存，notify 时再转发到 sender.send。抽象层（普通 / 紧急通知）和实现层（邮件 / 短信）因此各自独立扩展。运行会打印：

短信：[紧急] 服务器 CPU 过高
邮件：日报已生成

7. Python 示例

from typing import Protocol


# 实现层接口（协议）：定义“发送消息”能力，具体渠道后续实现，鸭子类型即可接入
class MessageSender(Protocol):
    def send(self, content: str) -> None:
        ...


# 具体实现 A：邮件渠道（实现维度）。无需显式继承，满足协议即生效
class EmailSender:
    def send(self, content: str) -> None:
        print(f"邮件：{content}")


# 具体实现 B：短信渠道（实现维度）
class SmsSender:
    def send(self, content: str) -> None:
        print(f"短信：{content}")


# 抽象层：构造时接住一个 sender 实现对象，用组合而非继承连接渠道
class Notification:
    def __init__(self, sender: MessageSender) -> None:
        self.sender = sender

    def notify(self, content: str) -> None:
        self.sender.send(content)


# 抽象层变体：紧急通知，属于“通知类型”维度，独立于渠道维度
class UrgentNotification(Notification):
    def notify(self, content: str) -> None:
        self.sender.send(f"[紧急] {content}")


# 运行时自由组合两个维度，无需为每种组合写一个类
UrgentNotification(SmsSender()).notify("服务器 CPU 过高")
Notification(EmailSender()).notify("日报已生成")

8. 优缺点

优点缺点
避免多维继承组合爆炸。需要先识别稳定的变化维度。
抽象和实现可独立扩展。比直接继承多一层接口和组合关系。
符合组合优于继承。对初学者不如适配器、外观直观。

9. 和相似模式的区别

模式重点区别
桥接拆分两个变化维度通常在设计前期主动使用。
适配器兼容已有接口通常在已有接口不匹配时补救。
策略替换算法策略多关注行为算法，桥接关注结构维度解耦。
装饰器增强功能装饰器保持相同接口，动态给对象“加料”（日志、缓存等）；桥接则拆分抽象与实现两个维度解耦，关注结构而非增强。
组合树形整体-部分组合用「同一个接口」统一处理叶子与容器；桥接是「两个不同接口」各自独立变。两者都靠组合而非继承，容易混。详细对比见 组合模式笔记 9.1 节。

一句话区分：简单包装只是套壳，仍把抽象和实现绑在一起；装饰器不改签名，但给对象“加料”增强功能；桥接恰恰是把抽象和实现拆成两层用组合连接，专门解决两个变化维度的组合爆炸 —— 这才是它和“简单封装”的本质不同。

10. 练习题

报表有 PDF、Excel 两种格式，输出位置有本地文件、对象存储两种。请用桥接模式避免 PdfLocalReport、PdfOssReport 这类组合类。

参考思路：格式作为抽象层，存储作为实现层；报表对象持有 ReportStorage。

今日总结

桥接模式的核心是“拆开两个变化维度，再用组合连接”。它不是为了多写接口，而是为了避免继承组合爆炸。
