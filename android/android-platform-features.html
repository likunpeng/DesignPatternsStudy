Android 平台核心特性

Android 的难点不只是写页面，而是让应用在系统随时暂停、重建、回收和切换设备环境时，依然正确、流畅且安全。

1. 为什么先学 Android 平台特性

在网页或桌面程序里，开发者通常能较稳定地控制窗口和进程；Android 不一样。系统要在有限电量、内存和多种设备环境中协调大量应用，因此它会主动暂停页面、回收后台进程、重新创建界面，并严格限制权限和后台行为。

因此，Android 代码不能只按“用户点按钮 → 显示结果”来判断对错，还必须回答：切后台后怎么办？旋转屏幕后数据还在吗？网络慢时会不会卡住？用户拒绝权限后页面是否可用？

2. 一张总览图：十个技术点如何关联

用户操作 / 系统事件
        ↓
Activity、Service、Receiver、Provider（四大组件）
        ↓
生命周期 + Intent + 权限
        ↓
主线程 / 后台任务 + 资源适配
        ↓
进程可能被回收，状态需要恢复
        ↓
沙箱安全 + 多设备、多系统版本兼容

下面十点不是彼此独立的知识：例如用户从后台回来时，生命周期决定回调；如果进程已被回收，状态恢复就变得关键；如果回来时重新拉取数据，耗时工作又不能阻塞主线程。

3. Activity 生命周期

Activity 可以粗略理解为一个页面的宿主。生命周期描述它从创建、可见、可交互，到被遮挡、停止和销毁的过程。系统触发这些阶段，应用只能在对应回调中做合适的事。

回调状态适合做什么不要做什么
onCreate()创建初始化 UI、读取 Intent 参数、恢复轻量状态执行长时间网络请求
onStart()可见开始与“可见”相关的轻量工作假设已经能稳定交互
onResume()可交互恢复页面交互、必要时刷新或订阅前台资源每次都无条件请求网络
onPause()失去焦点暂停相机预览、动画、传感器等独占资源做耗时保存；它应尽快返回
onStop()不可见停止不再需要的可见性相关工作认为进程一定还会存活
onDestroy()销毁释放明确拥有的资源依赖它保存重要数据

从其他页面返回

假设 A 页面打开 B 页面，A 完全被 B 覆盖，然后 B 关闭并回到 A：

A：onPause() → onStop()
B：显示并交互
B：关闭
A：onRestart() → onStart() → onResume()

onRestart() 表示 Activity 已停止、现在准备再次启动；onResume() 表示它重新可交互。若只是权限弹窗、透明页面等没有让 A 完全不可见，A 可能只经历 onPause() → onResume()。所以“回来后需要恢复交互”的逻辑，通常优先考虑 onResume()，而不是只写在 onRestart()。

从后台回前台

正常情况：onPause() → onStop() → [后台] → onRestart() → onStart() → onResume()
进程被回收：onPause() → onStop() → [系统杀进程] → onCreate() → onStart() → onResume()

第二种情况说明：回到前台不保证是原来的内存状态。页面变量、单例缓存都可能不存在，重要状态必须能从保存状态、数据库、文件或网络重新恢复。

4. 进程与任务：系统回收

Android 为每个应用提供进程和内存，但后台应用并不拥有永久生存权。系统内存紧张时，通常会优先回收较不重要的后台进程。用户从最近任务列表回来时，看到的是一个任务入口，不代表原来的进程和对象仍在。

数据类型示例更可靠的存放位置
瞬时 UI 状态展开/收起、选中的 Tab可保存的 UI 状态机制
页面业务状态商品详情、搜索结果ViewModel + 可重新加载的数据源
需要跨重启保存的数据草稿、设置、离线内容数据库、文件、偏好设置
敏感凭证登录令牌安全存储，并控制访问范围

AI 协同审查问题：如果提示“把结果放到一个全局变量，返回页面继续用”，要追问进程被杀、冷启动和多进程情况下如何恢复。

5. 配置变化与页面重建

屏幕旋转、夜间模式切换、语言变化、字体大小变化、平板/折叠屏尺寸变化等都属于配置变化。默认情况下，系统可能销毁旧 Activity 并创建新 Activity，以便应用重新加载合适的资源和布局。

竖屏 DetailActivity
      ↓ 旋转屏幕
旧实例：onPause() → onStop() → onDestroy()
新实例：onCreate() → onStart() → onResume()

这不是异常，而是 Android 的正常运行方式。不要为了“变量不丢”而一律禁止重建；更好的做法是把可恢复状态放在正确位置，让新页面按状态重新渲染。

检查点：输入到一半的表单、当前筛选条件、页面参数、列表位置，旋转后是否符合产品预期？不必所有内容都保留，但必须明确取舍。

6. 四大组件

组件主要职责典型例子协同开发关注点
Activity应用界面入口和页面宿主登录、商品详情、设置不要塞满网络、数据库和业务规则
Service执行不直接承载界面的任务音乐播放、导航、上传后台限制严格，不能当作“永远运行”
Broadcast Receiver接收广播事件网络状态、系统启动、通知操作回调时间短；复杂工作转交其他机制
Content Provider以统一接口共享或访问数据系统通讯录、跨 App 数据共享注意读写权限和数据暴露范围

四大组件通常要在 AndroidManifest.xml 中声明或由系统识别。它们的启动时机可能来自系统和其他应用，因此入口参数、权限检查和异常处理尤其重要。

7. Intent：Android 的“意图”通信

Intent 用于请求系统或其他组件执行某件事。它既可以明确指定目标组件，也可以只表达动作，让系统寻找能处理该动作的应用。

// 显式 Intent：打开本应用的详情页
startActivity(Intent(this, DetailActivity::class.java))

// 隐式 Intent：交给系统处理“查看网页”动作
startActivity(Intent(Intent.ACTION_VIEW, Uri.parse("https://example.com")))
  • 显式 Intent：明确打开哪个组件，常用于 App 内跳转。
  • 隐式 Intent：描述动作和数据，例如分享、拍照、打开地图、拨打电话。
  • Extras：携带参数，但只适合必要且较小的数据；大对象应通过 ID 或持久化数据传递。

检查点：外部 Intent 可能没有可处理的应用；传回来的数据也不应被默认信任。AI 写“调起相机/相册/浏览器”时，应检查目标可用性、权限和返回结果。

8. 权限模型

Android 把敏感能力隔离在权限之后，例如相机、麦克风、定位、通知、通讯录。很多权限不仅需要写入清单，还必须在运行时获得用户授权。

声明权限（Manifest）
        ↓
检查当前是否已授权
        ↓
必要时向用户发起运行时请求
        ↓
处理：允许 / 拒绝 / 不再询问
        ↓
仅在已授权时使用对应能力

权限被拒绝不是异常分支，而是正常用户选择。好的页面应该说明为什么需要权限，并在拒绝后提供降级体验或再次引导入口，而不是直接崩溃或无限弹窗。

安全原则：只请求功能真正需要的最小权限；不把敏感数据写进日志；不把 API 密钥硬编码进客户端。

9. 主线程与 ANR：后台任务不能阻塞界面

Android 的主线程负责响应点击、测量布局、绘制界面。耗时工作若阻塞主线程，用户会感到卡顿；长时间无响应时，系统可能弹出 ANR（Application Not Responding，应用无响应）提示。

适合主线程不应直接在主线程做
更新 UI、处理短点击逻辑、展示加载状态网络请求、数据库大查询、图片解码、大文件读写、复杂加密或循环计算
 
// 思路示意：后台取数据，主线程更新界面
viewModelScope.launch {
    val product = repository.loadProduct(productId) // 不应阻塞 UI
    _uiState.value = ProductUiState.Content(product)
}

协同审查时，看到按钮点击事件里直接执行网络、文件或数据库逻辑，就应要求把耗时任务移出主线程，并展示 loading、成功和失败状态。

10. 资源与屏幕适配

Android 把文本、图片、尺寸、颜色、布局等放入资源目录，系统会依据设备语言、深浅色、屏幕密度和尺寸等配置选择更合适的资源。这是支持国际化和多设备适配的基础。

变化条件适配例子常见误区
语言中文、英文、阿拉伯文文本资源把文案硬编码在代码里
深浅色夜间模式颜色、图标只在浅色背景下测试
屏幕密度不同密度的图片资源用像素写死尺寸
屏幕尺寸/方向手机单列、平板双列、折叠屏展开布局假设所有手机宽度相同
字体大小系统字体放大后仍能阅读和操作固定高度导致文字被截断

实际开发应优先使用 dp（与密度无关的尺寸）和 sp（会随用户字体设置缩放的文字尺寸），而不是直接按 px 设计。AI 生成 UI 后，要在小屏、大屏、横屏、深色模式和字体放大场景下验证。

11. 应用沙箱与跨应用边界

默认情况下，每个 Android 应用运行在独立沙箱内，拥有各自的私有文件、数据库和进程身份。一个 App 不能随意读取另一个 App 的私有数据，这也是 Android 安全模型的重要基础。

  • App 私有数据应放在私有存储区，其他 App 无法直接访问。
  • 要分享文件或数据时，需使用受控机制，例如 Content Provider、分享 Intent 和临时访问授权。
  • 导出的组件可能被其他 App 调用，因此必须验证输入和权限，避免无意暴露内部能力。

常见错误是把本地文件路径直接暴露给外部应用，或把内部 Activity/Receiver 无限制导出。人机协同开发时，凡是涉及登录令牌、文件分享、深链和跨 App 调用，都应额外做安全评审。

12. 设备碎片化与系统版本差异

Android 设备的屏幕、芯片、厂商系统版本和后台策略差异很大。即使功能在一台模拟器上正常，也不代表在真机、旧系统、折叠屏或厂商定制系统上完全一致。

差异来源可能后果应对方式
Android 系统版本权限、通知、存储规则不同明确最低版本并做版本兼容分支
屏幕与形态布局溢出、横屏体验差响应式布局和多尺寸测试
厂商后台策略后台同步、推送、定位不稳定使用官方推荐任务机制并提供可见反馈
硬件能力相机、传感器、NFC 不一定存在运行前检测能力并提供降级路径

碎片化不意味着要为所有设备写特殊代码，而是要避免“默认存在、默认允许、默认不会重建”的假设。

13. AI 协同开发检查清单

  1. 页面数据是否能在旋转屏幕、切后台和进程回收后恢复或重新加载？
  2. 从页面返回或前后台切换时，onResume() 的逻辑会不会重复请求、重复订阅？
  3. 是否错误依赖 onDestroy() 保存关键数据？
  4. 网络、数据库、文件操作是否离开了主线程？
  5. 权限是否同时覆盖声明、请求、拒绝和降级体验？
  6. 外部 Intent、深链或组件输入是否做了合法性校验？
  7. 敏感数据和密钥是否避免硬编码、日志泄露与越权共享？
  8. UI 是否经过深色模式、字体放大、不同尺寸和横竖屏检查？
  9. 后台任务是否使用适合的系统机制，而非假设 Service 永远运行？
  10. 关键能力在不支持的设备或旧系统上是否有处理策略？

14. 练习题

场景：用户在“发布商品”页面填写标题和价格，点击选择图片后切到系统相册；这时用户旋转屏幕，再切到后台聊天，稍后回到 App。请回答：

  1. 发布页面至少可能经历哪些生命周期回调？
  2. 标题、价格和已选图片信息分别应如何避免丢失？
  3. 图片读取涉及哪些权限或安全边界？
  4. 压缩大图片时为什么不能放在主线程？

15. 参考答案或改进建议

页面跳转相册时，发布页通常会先 onPause()；若完全不可见，还会到 onStop()。从相册返回且原页面仍在内存中，常见恢复路径是 onRestart() → onStart() → onResume()，但若只是短暂遮挡也可能主要回到 onResume()。如果旋转引起重建，旧实例会销毁，新实例重新进入 onCreate()。

标题和价格属于可恢复表单状态；图片应保存可重新访问的 URI 或业务 ID，而不是把整张 Bitmap 塞进 Intent 或内存变量。读取图片要使用系统授予的访问能力，并处理用户取消和无权限情况。图片压缩、上传和解析必须在后台执行，UI 仅展示进度、结果或错误。

今日总结

Android 的核心约束是：系统拥有生命周期和资源调度权，应用必须接受页面会暂停、重建，进程会被回收，设备环境会变化。后续与 AI 协同开发时，优先审查生命周期、状态恢复、权限、主线程和适配；这五项决定了功能是否能从“演示可用”变成“真实可用”。
