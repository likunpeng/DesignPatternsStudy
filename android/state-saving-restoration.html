Android 状态保存与恢复

页面旋转、切后台或进程被系统回收后，正确的目标不是“变量永远不丢”，而是让用户回到合理、可继续完成任务的状态。

Android 基础State SavingViewModelJetpack Compose

今日目标

  • 区分配置变化、进程回收和冷启动三种情况。
  • 知道数据该放在 Compose 状态、ViewModel、SavedStateHandle 还是数据库。
  • 避免把“状态保存”误解为把所有对象都塞进 Bundle。
  • 建立一条面向 AI 协同开发的 Android 速学路线。

1. 这个主题解决什么问题

用户在发布商品页填了一半标题，旋转屏幕、切到微信，或后台太久导致进程被系统回收。若数据只放在 Activity 或 Composable 的内存变量里，返回时页面可能重新加载，输入内容和当前步骤都会丢失。

状态保存的价值是：在系统生命周期不可控的前提下，明确哪些内容可以丢、哪些必须恢复，以及从哪里恢复。

2. 先区分三种场景

场景内存中的 ViewModel普通变量典型策略
配置变化通常仍可保留Activity/Compose 实例重建后丢失ViewModel 保存页面状态
进程被系统回收丢失丢失SavedStateHandle 保存轻量恢复参数；数据层重新加载
用户完全关闭后冷启动丢失丢失数据库、文件、账号服务等持久化数据恢复

关键结论：ViewModel 能解决配置变化，不等于能抵抗进程被系统回收。

3. 状态应该放在哪里

内容例子推荐位置原因
短暂 UI 状态密码是否显示、弹窗是否展开Compose remember离开/重建后可接受丢失
可恢复 UI 状态当前 Tab、输入框文字、筛选项rememberSaveable 或 SavedStateHandle适合保存小型、可序列化内容
页面状态加载中、商品详情、错误提示ViewModel + StateFlow让 UI 与生命周期解耦
长期业务数据草稿、收藏、离线订单Room / DataStore / 文件进程死亡、重启后仍应存在
路由恢复参数商品 ID、搜索关键词SavedStateHandle恢复后据此向数据层重新读取

4. Compose：remember 与 rememberSaveable

remember 只在当前 Composable 留在内存时保留值；页面实例重建后可能丢失。rememberSaveable 会使用保存状态机制恢复适合保存的小型值，例如文本、布尔值、枚举和 ID。

@Composable
fun SearchScreen() {
    var keyword by rememberSaveable { mutableStateOf("") }

    TextField(
        value = keyword,
        onValueChange = { keyword = it },
        label = { Text("搜索") },
    )
}

不要把整个商品列表、Bitmap、大型响应对象塞进 rememberSaveable。保存关键词或 ID，重新从数据层读取才是更稳的方式。

5. ViewModel：保存页面状态，不持有页面

ViewModel 适合持有页面的 UiState，例如加载、成功、失败、当前编辑值。它不应保存 Activity、View、Composable 或其他 UI 引用，否则可能造成内存泄漏。

data class EditUiState(
    val title: String = "",
    val saving: Boolean = false,
    val error: String? = null,
)

class EditProductViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(EditUiState())
    val uiState: StateFlow<EditUiState> = _uiState

    fun updateTitle(value: String) {
        _uiState.update { it.copy(title = value) }
    }
}

Compose 读取 uiState 并派发事件；ViewModel 更新状态；UI 随状态刷新。这是状态驱动 UI 的基本协作方式。

6. SavedStateHandle：进程回收后的轻量恢复

SavedStateHandle 是 ViewModel 中用于保存可恢复状态的入口。适合存商品 ID、筛选条件、当前步骤等小数据；恢复后再通过 Repository 或数据库重建完整页面。

class ProductViewModel(
    private val savedStateHandle: SavedStateHandle,
    private val repository: ProductRepository,
) : ViewModel() {
    private val productId = savedStateHandle.getStateFlow("product_id", "")

    fun open(id: String) {
        savedStateHandle["product_id"] = id
        // 根据 id 重新加载完整商品数据
    }
}

不要误用：它不是数据库，更不是大对象缓存。保存“如何重新找到数据”的线索，而不是复制整份数据。

7. 数据分层：恢复不等于缓存一切

稳定的恢复流程通常是：

SavedStateHandle：保存 productId / filter
        ↓
ViewModel：根据恢复参数发起加载
        ↓
Repository：决定读网络、Room 缓存或文件
        ↓
UiState：渲染加载、内容、失败状态

这就是数据分层的意义：UI 只关心状态；ViewModel 负责页面逻辑；Repository 负责数据来源。进程死亡后，内存状态可以消失，但恢复入口和业务数据仍然可用。

8. AI 协同开发的检查清单

  1. 这个状态在旋转、进程回收、冷启动后分别应不应该恢复？
  2. 是否把所有状态都塞进 ViewModel，却没有持久化真正重要的数据？
  3. 是否错误把大列表、Bitmap、网络响应对象放进 Bundle 或 SavedStateHandle？
  4. ViewModel 是否持有 Activity、Context、View 或 Compose UI 引用？
  5. 恢复时是否只有 ID/筛选条件，然后通过数据层重新加载？
  6. 加载、空数据、错误和重试是否都是明确 UiState？

10. 练习题

做一个“编辑个人资料”页面：昵称、性别、头像 URI 和保存状态。请分别选择它们应该放在哪里，并说明用户旋转屏幕、切后台后进程被杀、重新冷启动时的恢复策略。

11. 参考答案或改进建议

昵称和性别可作为可恢复表单状态放在 ViewModel，并用 SavedStateHandle 保存轻量草稿；头像保存 URI 或上传后的文件 ID，不保存 Bitmap；保存中的 loading/error 是短暂 UiState；若草稿必须跨冷启动保留，应落到数据库或本地草稿文件。进程恢复后，根据 URI/ID 和草稿数据重新构建页面。

今日总结

状态恢复的核心不是记住更多变量，而是把数据放到正确层次：短暂 UI 用 remember，轻量可恢复状态用 rememberSaveable 或 SavedStateHandle，页面状态用 ViewModel，长期业务数据用持久化存储。下一步建议学习 Jetpack Compose 的状态与重组。
