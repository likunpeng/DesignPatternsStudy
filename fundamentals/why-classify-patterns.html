设计模式全景：为什么这样分类

23 个 GoF 设计模式不是随机堆在一起的。它们被分成创建型、结构型、行为型三类，本质是一张「写代码时遇到问题该去哪找解法」的地图。本文先讲清楚这张地图怎么画出来的，再用一句话带过每一个模式，方便你后面逐个深入。

前置基础 设计模式分类 23 个模式 三问模型

今日目标

  • 理解为什么 23 个模式要分成创建型、结构型、行为型三类。
  • 用一个「三问」模型记住每一类在解决什么问题。
  • 读完能对每一个模式说出一句话定位和典型场景。
  • 遇到「这两个模式好像差不多」时，知道怎么快速区分。

1. 先说清楚：分类是为了好找，不是为了背

如果你已经写了几年代码，大概率在不经意间用过某些设计模式——只是当时不知道它叫这个名字。比如用过一个全局配置对象（单例）、给函数加过缓存或日志（装饰器思想的雏形）、或者用事件通知过多个模块（观察者）。

设计模式被整理出来，最大的好处不是让你说话显得专业，而是当你面对一段越来越难改的代码时，能快速判断：「我遇到的，到底是哪一类问题？」 答案一旦清楚，该去 23 个模式里的哪几个里找灵感，也就清楚了。

所以分类本身不是重点，分类背后的那三个问题才是重点。记住三个问题，比记住 23 个名字有用得多。

2. 三问模型：创建、结构、行为

所有 23 个模式，都可以放进回答下面三个问题之一的抽屉里。这三个问题彼此正交：一个问题变了，通常不影响另外两个。

▍核心框架 · 三问模型

一段代码会随时间变复杂，无非在三个维度上出问题：对象怎么来、对象怎么组合、对象怎么协作。设计模式就是按这三个维度归类的。

🏗️一个生活类比

开一家餐厅：先要解决「食材从哪进货」（创建型），再解决「厨房、前厅、仓库怎么布局才不打架」（结构型），最后解决「服务员、厨师、采购之间怎么传话不混乱」（行为型）。三类问题同时存在，但各自独立。

三个抽屉各装什么
创建型对象怎么被造出来
结构型类/对象怎么组合
行为型对象怎么协作通信

遇到代码坏味道，先问自己：这是「造」「组合」还是「协作」的问题？答案决定去哪一类找模式。

3. 创建型：解决「对象怎么来」

当你发现代码里到处是 new、或者「该造哪个对象」的判断逻辑散落得到处都是，就该看这一类。它们不关心对象内部长什么样，只关心谁来决定造什么、怎么造。

模式一句话定位典型场景
单例（Singleton）保证一个类只有一个实例，并提供全局访问点。配置、日志、连接池等「全系统共用一个」的对象。
简单工厂（Simple Factory）用一个工厂函数根据参数返回不同产品对象。把散落在各处的 new 分支收口到一个地方。
工厂方法（Factory Method）把「造哪个产品」交给子类去决定。框架留扩展点，调用方只依赖产品接口。
抽象工厂（Abstract Factory）生产一族互相配套的产品对象。跨平台 UI 套件，保证多个产品组合一致。
建造者（Builder）把复杂对象的构建步骤拆开，支持不同装配。构造参数多、组合多变的报表 / 订单 / SQL。
原型（Prototype）通过复制已有实例来创建新对象。创建成本高、或需要大量相似初始状态的对象。

4. 结构型：解决「对象怎么组合」

这一类全部在回答一个问题：怎么把类和对象拼到一起，既灵活又不互相绑死？ 它们几乎都体现了「组合优于继承」：与其用继承把行为焊死在层级里，不如把能力拆成可拼装的部件。这也是为什么结构型最容易被人觉得「这几个长得像」。

模式一句话定位典型场景
适配器（Adapter）把一个接口转换成调用方期望的另一接口。接老系统 / 第三方 SDK，接口对不上。
装饰器（Decorator）不改原类，动态叠加新能力。日志、缓存、权限等横向能力组合。
代理（Proxy）为目标对象加一层替身，控制访问。懒加载、权限校验、远程调用、缓存。
外观（Facade）把一堆复杂子系统的调用打包成简单入口。降低调用方对子系统的认知负担。
桥接（Bridge）把「抽象」和「实现」两条变化轴分开，各自扩展。形状×颜色、设备×驱动等多维变化。
组合（Composite）用同一接口把对象组织成树，统一处理单个和整体。菜单、文件目录、UI 组件树。
享元（Flyweight）共享大量细粒度对象的公共部分，省内存。字符、棋子、连接等大量重复对象。

5. 行为型：解决「对象怎么协作」

这一类关心的是职责怎么分、消息怎么传、状态怎么变。对象已经造好、也组合好了，问题出在它们之间「说话的方式」——要么紧耦合、要么一个对象知道太多别人的事、要么流程写死不好换。

模式一句话定位典型场景
策略（Strategy）把可互换的算法封装成独立对象，运行时挑选。支付方式、折扣、排序规则。
模板方法（Template Method）固定算法骨架，把可变步骤留给子类。流程稳定但某些步骤不同的场景。
观察者（Observer）一对多，状态变化时自动通知订阅者。事件、消息推送、UI 刷新。
责任链（Chain of Responsibility）把请求串成一串处理者，谁合适谁处理。审批流、过滤器、中间件。
命令（Command）把请求封装成对象，支持撤销 / 队列 / 日志。撤销重做、任务队列、宏。
状态（State）把不同状态拆成独立类，状态自己决定下一步。订单状态机、连接状态、角色状态。
迭代器（Iterator）提供统一方式遍历集合，不暴露内部结构。自定义集合、树 / 图遍历。
中介者（Mediator）用中心对象协调一群对象，避免互相直接引用。聊天室、UI 组件联动、调度。
备忘录（Memento）不破坏封装地保存 / 恢复对象状态。撤销、快照、游戏存档。
访问者（Visitor）把对元素的新操作集中到访问者，元素结构稳定。对 AST / 文档树做多种统计或导出。
解释器（Interpreter）为简单文法定义解释规则，处理领域语言。规则引擎、表达式求值、配置 DSL。

6. 一个常见困惑：为什么有的模式看着像？

分类只是粗线条。真正动手时会发现，结构型内部好几个都像「包一层」，行为型里策略和状态也像。下面两对是最常被问到的，给你快速判别法。

桥接 vs 组合

两者结构图上都有「一个对象指向另一个对象」，但意图完全不同：桥接是让两个不同的接口各自独立变化（比如形状和颜色互不影响）；组合是让许多相同的接口组成一棵树（比如文件夹里套文件夹）。判别法：你是在「拆两条变化轴」还是「递归地组装同一种东西」？

维度桥接（Bridge）组合（Composite）
指向的对象另一种接口（实现维度）同一种接口（自身类型）
目的两条变化轴独立扩展统一处理单个对象和整体
结构形状横向两根轴交叉纵向一棵树

想看代码示例和更多对比，见组合模式里的「桥接 vs 组合」一节。

策略 vs 状态

两者都是「把可替换的行为抽成对象」：策略由调用方主动挑选用哪种算法；状态由对象内部的当前状态自动切换下一步走哪个分支。判别法：是谁在做选择？你在外面临时换，还是对象自己按状态流转？

维度策略（Strategy）状态（State）
谁决定用哪个调用方 / 运行时传入对象内部状态自动切换
关注点算法可互换状态流转与约束
典型例子支付方式、折扣规则订单状态机、连接状态

更多对照见策略模式里的「策略 vs 状态」一节。

记住：分类是「地图」，不是「牢笼」。有些模式会跨边界——比如装饰器既是结构型（包一层），也顺手改变了行为。先靠三问定位大方向，再进具体文章看细节，比死记类别更稳。

8. 练习题

下面三个场景，分别属于哪一类？如果再进一步，你第一反应会用哪个模式？

  • 系统里到处 new MySQLOrderRepository()，以后要换 PostgreSQL，得改十几处。
  • 给一个支付接口动态加上「限流 + 日志 + 重试」三件套，且不同接口组合不同。
  • 订单有「待支付 / 已支付 / 已发货 / 已完成」，每种状态下允许的操作和跳转都不一样。

9. 参考答案或改进建议

  • 场景一 → 创建型。问题在「对象怎么来、由谁决定」。优先考虑用工厂方法 / 抽象工厂把创建收口，配合依赖倒置让业务只依赖仓库接口。
  • 场景二 → 结构型。问题在「给对象动态加能力、且组合可变」。装饰器最贴合：每个能力一个装饰器，按需嵌套。
  • 场景三 → 行为型。问题在「状态流转与约束」。状态模式最贴合：把每种状态拆成独立类，状态自己决定下一步能去哪。

今日总结

23 个模式分成三类，不是为了考试，而是给你一张「出问题了该去哪找」的地图。记住三问——对象怎么来（创建型）、怎么组合（结构型）、怎么协作（行为型）——你就能在看到坏代码时快速定位方向，再进具体文章挑模式。分类是入口，不是终点；真正的能力是带着这张地图去读每一个模式的细节和取舍。
