## 评审 adapter 教程（初学者友好度）
- 结论：结构完整(10部分齐全)，有概念速览+双语+练习，但对纯初学者有3个卡点
- 卡点1：生活类比(转接头)未显式映射到代码角色 Client/Target/Adapter/Adaptee，初学者面对代码不知谁是谁
- 卡点2：第9部分对比了外观/代理，但缺装饰器(装饰器也实现相同接口，初学者最易混淆)
- 卡点3：缺"不用适配器的坏代码 vs 用好代码"并排对比；概念定义首句用"接口"对零基础有门槛
- 后续写其他模式复用准则：概念速览做"类比→角色"映射；相似模式对比必须含装饰器(若适用)；必要时加接口白话解释

## 重写 adapter 教程反例（前因后果结构）
- 用户指出 adapter-pattern.html 第1部分反例"看不出问题"：只展示单位换算、没有新接口、只有一个调用点、缺前因后果
- 按"前因→触发变化→后果→引出正例"重写第1部分反例：先给单 SDK(LegacyPaySdk) 现状，再接入第二个差异很大的 SDK(NewPaySdk: processPayment/元)，展示业务被迫同时依赖两套方法名+单位，点明"从1到N"的恶化(下单/退款/对账都会用到)
- 同步扩展第6部分(TS)与第7部分(Python)：各加 NewPayAdapter，让两个 SDK 都收口到 PaymentGateway，与反例两个 SDK 对齐，正反例真正咬合
- 教学要点：反例价值在于让初学者"感到别扭"，正例一出现才"哦原来如此"；单调用点撑不起"散落各处"的结论

## 重写 proxy 教程反例（前因后果结构）
- 用户指出 proxy-pattern.html 第1部分反例只是个无意义转发函数，看不出为什么不好
- 按"前因→触发变化→后果"重写：前因(直连 RemoteUserRepository 重复打远程)→触发变化(产品要求加权限+避免重复远程，业务被迫在每个调用点手写 if+cache)→后果(权限/缓存散落、远程被穿透、换调用点要重写)
- 同步扩展第6部分(TS)与第7部分(Python)：代理收口"缓存+权限"到同一个 findName/find_name，类名 CachedUserRepositoryProxy，构造时接 real + canRead 闭包；业务只认 UserRepository 接口，调用方式不变
- 与 adapter 教程统一手法：反例制造痛点(无控制点)，正例把控制逻辑收口到代理一处；明确代理≠简单封装(控制访问而非增强功能)
