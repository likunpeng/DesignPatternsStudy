# 2026-07-29

## 修改 structural/adapter-pattern.html
- 用户反馈：教程开头用「笔记本+投影仪」类比，但第1节反例和第6/7节代码突然换成「支付 SDK」场景，两套画面增加认知负担。
- 修复：将全文主线统一为「笔记本 → 投影仪/电视 → 转接头」单一故事线（反例、TS 示例、Python 示例全部改用 Display/Projector/TV 命名）。
- 支付 SDK 降为第6节末尾一段「真实场景延伸」小注，明确标注为延伸而非主线，避免分裂心智模型。
- 经验：本项目的设计模式教程应保持「类比场景 == 代码场景」一致；生活类比与代码例若用不同领域会明显增加初学者学习成本。

## 第2轮：重写第1节
- 用户反馈：第1节用「笔记本+投影仪」类比正确了，但堆了「前因/触发变化/后果」三段叙事，绕了一大圈才回到笔记本，核心问题被埋得太深。
- 修复：删掉三段叙事，重写为「笔记本视角 → 直接说它要做什么 → 一段小代码展示耦合 → 点出适配器思路」的紧凑结构，让笔记本成为整节主角。
- 新第1节核心：3台设备（投影仪/电视/显示器）的小代码片段直接演示耦合问题 → 笔记本真正的问题（方法名+信号格式全混）→ 适配器 = 在中间塞翻译。
- 经验：「这个模式解决什么问题」一节应直接陈述主角的真实处境，不要为了铺垫动机而堆叙事；初学者最快理解的方式是「直接看到主角为难在哪」。

## 第3轮：统一类比口径为物理口
- 用户反馈：第2轮虽然场景统一了，但用了 `show`/`project`/`play` 这类抽象方法名做类比，初学者觉得"不好理解"；明确要求"直接使用 USB-C / HDMI"。
- 修复：全文去掉 `show`/`project`/`play`/`Display` 抽象名，统一成"笔记本(USB-C) → 转接头 → 投影仪(HDMI)"的物理口说法。代码方法名也改成直接对应物理口：`receiveUsbC`(Target) / `receiveHdmi`(Adaptee) / `UsbCToHdmiAdapter`(Adapter)，让代码一眼能和生活类比对上。
- 速览、生活类比(第2节)、第1节、第6/7节代码现全部一套话；支付 SDK 仍是第6节末尾延伸小注。
- 教训：本项目教程类比优先用具体实物/物理口（USB-C↔HDMI），不要编造抽象方法名当类比；且生活类比与代码例的方法命名要能互相印证，否则初学者仍会觉得"代码和前面说的不是一回事"。
